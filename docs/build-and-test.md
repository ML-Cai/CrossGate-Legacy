# Build and test

Use these commands from the repository root. On Windows use an x64 Visual Studio
Developer Command Prompt with MSVC AddressSanitizer installed. Install Ninja,
CMake 3.21+ (for presets), the Vulkan SDK including glslc, and Python with development
headers. Install the project's dependencies first:

```powershell
python setup_requirements.py --build_type RelWithDebInfo
cmake --preset dev
cmake --build --preset dev
ctest --preset dev-unit
```

Activate the intended Python environment before configuring; alternatively pass
`-DPython3_EXECUTABLE=...`. A worktree can reuse an existing dependency installation
by passing `-DCMAKE_PREFIX_PATH=.../third_party/build/RelWithDebInfo` to configure.
Put personal overrides in ignored `CMakeUserPresets.json`. Build directories are
`build/dev` and `build/asan`; older build directories are not updated by these presets.
The ordinary `cmake -S . -B ...` interface still works with CMake 3.16+.

## Test groups

| Label / dev preset | Runtime requirements |
| --- | --- |
| `unit` / `dev-unit` | No window, GPU initialization or installed game assets; synthetic files are generated by tests. Includes the Python/NumPy binding test when tools are enabled. The full project still requires desktop SDK dependencies; an SDK-free subset is described below. |
| `desktop` / `dev-desktop` | Vulkan device and desktop/window support. Includes rendering and client integration tests. |
| `assets` / `dev-assets` | Installed game corpus; some tests also need a desktop. |
| `memory` / `dev-memory` | Reader ownership, bounded scratch/cache, cancellation and scene teardown tests. Includes desktop/corpus tests. |

Labels overlap. The mixed `test_scene_lifecycle` executable is conservatively
marked desktop/assets/memory, including its CPU-only cases. These labels describe
runtime requirements, not independently buildable core modules. Future scene
refactoring can separate the mixed executable.

Presets run one test at a time because existing cases share generated settings and
working directories. Desktop tests also use a CTest resource lock to avoid
concurrent GPU/window tests. Every discovered case has a timeout; presets fail if
no test matches. Inspect the selected cases before running on another machine:

```powershell
ctest --preset dev-unit -N
ctest --test-dir build/dev --show-only=json-v1
ctest --test-dir build/dev --output-on-failure --no-tests=error
```

The last command runs **all** tests, without exclusions. Corpus tests read
`build/dev/bin/settings.ini`; set `General.EngineRootPath` to the directory containing
`bin/` and `map/`. Desktop map tests need `map/0/2100.dat` and `map/0/100.dat`.
Do not replace this shared test INI with a benchmark/server-demo configuration.
Settings generation can recreate this INI after changes to the settings schema.
Missing assets or GPU support are failures, not silently skipped tests.

## AddressSanitizer and resource lifetime

```powershell
cmake --preset asan
cmake --build --preset asan
ctest --preset asan-unit
ctest --preset asan-memory
```

Client startup integration tests allow 1200 frames / 100 seconds under ASan,
compared with 240 frames / 50 seconds normally. Instrumented asynchronous asset
initialization can outlast the ordinary frame limit; scene readiness, expected
errors, clean shutdown and Vulkan validation checks remain required.

Configure the ASan build's own `bin/settings.ini` before corpus tests. Tools are
disabled in this preset, so ASan does not need to load an instrumented Python module.
`CGL_ENABLE_ASAN=ON` also works with a custom build directory. MSVC uses
`/fsanitize=address`, debug information and non-incremental linking. STL container
annotations are disabled for compatibility with existing unsanitized dependencies;
this reduces container-boundary coverage. GCC/Clang use `-fsanitize=address` and
frame pointers. These compiler branches are not a claim of completed platform ports.

ASan catches memory access errors; a passing run alone does not prove absence of
leaks, especially on Windows where this configuration does not provide LeakSanitizer.
Ownership tests additionally check released references, pending-work cleanup and
bounded retained buffers. GPU tests check validation diagnostics and teardown.
Repeated scene/reload tests and process/GPU memory measurements remain necessary
for resource-cache changes. Driver allocations and cache residency must be tracked
separately from leaked objects. Do not compare ASan FPS against release performance.

For repeatable teardown/cancellation checks:

```powershell
ctest --test-dir build/asan -L memory --repeat until-fail:5 --output-on-failure --no-tests=error
```

## Bounded runtime telemetry

General gameplay can use the same CPU frame-time mean/nearest-rank percentile
calculation as the crowd benchmark. In a custom INI:

```ini
[Telemetry]
Enabled=true
ReportPath=runtime-summary.json
```

Telemetry is off by default; the supplied server-demo100.ini enables it. Empty
ReportPath keeps the periodic console/title diagnostics without writing a file.
Report paths are relative to the process working directory; the parent must exist.
Use a different path from Benchmark.ReportPath. A failed report write is reported
as a client error and still goes through normal engine cleanup.

The runtime collector keeps exactly 512 sample slots. Its summary describes the
last up to 512 completed gameplay frames, not a fixed number of seconds or the
whole session; total_samples is a separate lifetime count. Initial loading is
excluded. Restart/transition stalls after gameplay starts remain observable.
Zero drawn actors can be correct for non-map scenes. Drawing only updates render
counters; sampling happens after the frame has been recorded/presented. Console
summary output is limited to every two seconds and its cost is included in that
frame's duration. Sample insertion and rolling summaries do not allocate heap
storage. World rendering still has its existing allocations; telemetry does not
claim to remove those.

FPS is 1000 divided by mean CPU frame duration. Update, render-loop and map-sort
CPU times are separate; render-loop time includes presentation/fence waits, not
GPU timestamp-query execution time. The title shows the previous completed frame
window when the local snapshot refreshes. When telemetry is disabled it says so.

Report status describes clean/error exit, not appearance-loading completion. A
frame-limited run can exit during initial loading with zero gameplay samples;
check total_samples before interpreting a report.

JSON reports include frame p50/p95/p99/max, counts above 1000/30 ms, draw counts and
resource snapshots taken before teardown. Animation and map RGBA fields count
cache-owned texture payload, with hover-outline bytes separate. Animation pending
bytes are the current CPU/decode or upload reservation, not an exact GPU resident
allocation; do not add them to other fields as a process/VRAM total. Driver,
pipeline, descriptor, staging, allocator overhead and reader scratch/cache bytes
are not covered. Usage snapshots borrow no resource ownership and clear to zero
when their caches are cleared.

The benchmark retains its existing bounded-by-config whole-run vectors, cold-load
latency reports and warmup behavior. Its full-run FPS/percentiles can differ from
the runtime collector's last-512-frame values. Basic runtime telemetry does not
yet provide per-request latency, hit/miss counts or GPU timers;
those can be added at the responsible resource layers with later cache work.

## Idle cache maintenance at scene transitions

```ini
[CacheMaintenance]
Enabled=true
AnimationTargetMiB=64
MapTargetMiB=64
```

These are the defaults, in the range 0..1024 MiB. They are soft **total cached
payload** targets, not replacements for the animation hard loading budget or a
physical VRAM limit. A zero target drops every eligible ready entry at a transition.
An additional fixed 1 MiB warm budget applies to hover outlines. Soft count limits
of two maps and sixteen outlines also bound CPU-only/zero-texture cache entries.
A zero byte target also sets that cache count target to zero. Live references
can keep usage above any target; they are never forcibly invalidated.

Ready animation, map and outline caches track successful acquisition/readiness
lookups and publication in least-recently-used order. After the old scene has
exited and been destroyed, before the next scene loads, the engine trims entries
that have no shared owners outside the cache until the target is met or no more
eligible entries remain. Recency metadata is stored with the cache entry and is
removed with it. There is no age-in-seconds/TTL policy in this step.

Reference count alone is **not** evidence of GPU completion: recorded draws borrow
raw renderer pointers. ClientEngine now moves cache-only victims to a deferred
ownership queue, tagged with the last successful graphics submission serial.
Frame slots record their serial only after successful queue submission. A
successful wait on a reused slot's fence advances completion; failed waits or
submissions do not. This proof applies to the single graphics queue used by this
renderer, not presentation or arbitrary future transfer/compute queues.

Each update collects entries whose serial has completed. Collection can lag GPU
completion by a frame/slot reuse; it never adds a fence poll, device waitIdle or
queue wait to maintenance. Allocation failure preserves the current cache entry;
earlier transfers stay queued. There are no raw owning callbacks or detached
resources. Pending decode/upload slots are not retirement candidates. Scene exit
still cancels/drains pending uploads, and shutdown still waits before clearing
both ready and retired ownership, before render-pass/device destruction.

The explicit library trimUnused API remains blocking for offline maintenance and
existing callers/tests. Do not use it for in-frame pressure eviction. retireUnused
and collectRetired are internal owner-thread APIs: callers must supply this
renderer/device lifetime's last submitted and acknowledged-complete serials.
Never substitute a CPU frame number or clear a live retired queue.

Telemetry keeps animation_rgba_bytes / map_rgba_bytes / outline_rgba_bytes as
ready-cache payload. Separate animation_retired_bytes, animation_retired_clips,
map_retired_bytes, outline_retired_bytes, retired_maps and retired_outlines show
queued ownership. animation_evictions, animation_evicted_bytes and
map_outline_evictions count cache removals, not completed GPU frees. Counters
reset on clear. Ready + retired + pending animation payload/reservation counts
against the hard animation budget; retiring an entry does not create free budget.
These are not physical VRAM or total process RAM measurements.

Warm resources below targets and externally held resources remain retained.
Progressive appearance loading now defers on temporary budget pressure and can
evict cache-only ready clips during gameplay. Synchronous scene/map loading still
fails if a different scene cannot fit alongside queued allocations; asynchronous
scene-entry backpressure remains follow-up work. Reacquiring the same key before
collection now restores the same ready resource without allocating another copy.
Soft targets are not strict peak-memory limits. Retirement avoids a device-idle
wait; synchronous map loading, upload cancellation waits and shutdown
synchronization remain.

CPU tests cover LRU/pins, transfer allocation failure, zero-byte entries, ordering,
overflow, 1000 retirement/collection cycles and submission acknowledgement. Real
Vulkan tests submit map100 draws, drop scene owners, retire/reload three times,
verify weak references survive before fence acknowledgement and expire after it,
keep a pinned clip alive, and ensure retired bytes remain charged to the budget.
The existing blocking-maintenance tests remain. ASan, weak-reference expiry and
validation checks supplement each other; none alone proves absence of all leaks.

## Progressive animation budget pressure

AnimationBuilder distinguishes metadata admission failure from corrupt/missing
assets. AnimationBudgetExceeded includes required RGBA bytes and is raised before
palette/pixel reads. A progressive request that can fit the configured total and
32 MiB per-progressive-clip limits returns nullptr while free budget is too small,
retains one bounded request/required-byte record, and retries after collection.
It does not repeatedly decode pixels or permanently blacklist that appearance.
The background and owner-thread decode paths use the same admission behavior.
At zero free bytes, the background path initially records a one-byte admission
minimum; metadata planning determines the exact size once capacity becomes
available. This may require another pressure cycle before pixels can be decoded.
Missing/corrupt resources, invalid directions and clips exceeding a total/per-clip
limit remain real errors. Synchronous acquire keeps its existing throwing contract.

ClientEngine calls maintainStreaming once per update. It collects at most eight
completed clips, one map and two outlines; zero-byte entries count toward these
limits. When a progressive request is waiting, pressure retirement selects only
cache-only LRU clips, at most eight per scan, no more than once per sixteen update
calls. Cancelling/replacing a wait does not reset the scan cooldown.
Already-retired bytes are credited as future capacity before selecting
more victims, but cannot be used for an upload until acknowledged completion and
collection. No new waitIdle/fence wait is added. CacheMaintenance.Enabled=false
disables automatic pressure eviction as well as transition eviction; bounded
collection continues because pending GPU ownership must eventually be released.

These are work-count bounds, not hard CPU-millisecond bounds. Candidate LRU scans
still visit/sort the current cache. GPU object destruction and freeing a large map
can take driver/allocator time. If all clips remain pinned, the request keeps its
placeholder and waits without evicting live assets; it is not guaranteed to become
ready under an insufficient working-set budget. Increasing budget or releasing
owners can unblock it. Cancel/scene exit clears the wait record; shrinking budget
below an already-known waiting clip minimum is rejected until that wait is cancelled.

The server demo may switch a waiting (no upload submitted) request to the current
visible/prefetch candidate, or cancel it when no candidate remains. It still
finishes submitted uploads rather than cancelling GPU work on every snapshot.
Full scheduler preemption/fairness is not implemented here.

Telemetry adds animation_budget_deferrals (number of admission-deferral returns,
not elapsed frames) and animation_waiting_for_budget. Existing pending bytes stay
zero during a pure budget wait. Ready + retired + pending accounting remains in
force; these counters are not driver VRAM measurements.

Tests cover required-byte metadata errors without pixel reads, pinned pressure,
retired capacity remaining charged until frame-fence completion, eventual retry,
disabled eviction, candidate cancellation/reappearance, real errors remaining
errors, bounded destruction/retirement including zero-byte entries, and sixteen
small-budget snapshot batches cycling through eight distinct character appearances.

See [resource-streaming-plan.md](resource-streaming-plan.md) for the remaining
resource and rendering work and the estimated PR boundaries.

## Reusing retired assets before collection

Animation, map and hover-outline retirement retains their existing ready-cache
keys. A key index borrows stable list iterators, owning no secondary GPU resource
references. It replaces the older unkeyed retirement queue; bounded collection,
serial ordering and all previous lifetime tests remain in use.

acquire and acquireProgressive check retired ownership after a ready-cache miss,
before decoding, uploads or free-budget admission. A retired hit inserts into the
ready cache before removing retired ownership/index metadata. If destination
insertion fails, retired ownership remains intact. If retirement index insertion
fails, the new list node is rolled back and the ready cache keeps its owner.
All operations belong to one owner thread; callbacks cannot re-enter the library.

Restoration does not free or reallocate a GPU object. The same allocation moves
from retired accounting to ready accounting, so ready + retired + pending usage
is unchanged even when the animation budget is exactly full. A subsequent
retirement uses the renderer's latest submitted serial, including draws after
restoration; an older completion token must not free it. An unrelated pending
CPU decode/upload or budget-wait request is not cancelled or replaced by a hit.
findReady remains a ready-only lookup; explicit acquisition performs restoration.

Collection wins if it has already removed that key: a later acquire does a normal
load and remains subject to the hard budget. Keys still assume one library's live
device/render pass and unchanged resource corpus. Device/pass validation runs
before restoration. Map keys keep absolute lexical normalization; outline scales
must remain valid/finite. Clear after GPU completion when reloading files or
changing device/pass. This does not add file-version detection, simultaneous-device
sharing or asynchronous map loading.

Telemetry adds animation_reused_clips, map_reuses and outline_reuses. These count
retired-to-ready restorations, not ordinary ready-cache hits, new uploads or GPU
frees; clear resets them. Eviction counters still count removal from ready cache,
even if that resource is subsequently reused rather than destroyed.

CPU tests include duplicate/missing keys, failed restore and index insertion,
middle-node restoration, zero-byte/bounded collection, exact payload accounting
and 1000 restore/retire cycles with no stale key index. Real Vulkan tests re-enter
map100 three times at an exactly full animation budget, assert clip/map/outline
object identity and zero graphic-file reads, and require the latest fence before
final release. Progressive reuse is also tested with zero free budget and with an
unrelated decoder reservation still active.

## Scene animation admission

Map and animation-preview scenes plan their complete animation working set from
metadata before acquiring clips (and before loading the map). Invalid metadata or
a set larger than the hard animation budget fails explicitly without allocating
animation pixels. This budget covers animations, not map textures or driver VRAM.

Temporary pressure from old ready/retired allocations produces a loading state.
The owner thread retries admission on subsequent updates; normal blank-frame
submissions keep frame-fence completion advancing. Existing bounded maintenance
collects completed allocations and retires unheld ready clips under pressure.
A budget wait holds no decoded pixels or submitted upload. Metadata is not
replanned on every waiting frame. Already acquired clips remain strongly owned
until entry finishes, is restarted, or is cancelled by a scene change.

The map scene publishes its player only after all sixteen directional clips are
ready; the preview publishes both sprites together. Movement and animation updates
are skipped while waiting. SceneLoadProgress exposes completed/total clips and
required animation bytes, and the window title shows loading progress. Reports add
scene_loading, scene_load_completed and scene_load_total; loading frames are
excluded from gameplay FPS samples. Benchmark startup retains its existing path.

This is frame-driven capacity admission, not fully asynchronous scene loading:
map parsing, successful synchronous clip decode/upload and map upload can still
stall a frame. External owners can pin enough resources to keep a scene waiting;
disabled pressure eviction can also prevent progress. No timeout forcibly frees
live resources. Exit cancels the wait and releases partial ownership; GPU lifetime
still follows acknowledged submissions and shutdown ordering.

Headless tests cover whole-set admission, overflow, duplicate requests, partial
ownership and exception cleanup. Vulkan lifecycle tests cover waiting for old
frames, movement suppression, 15/16-clip restart/cancellation, impossible budgets
before map allocation, and atomic preview sprite publication.

## Visible-demand scheduling and nonblocking CPU discard

Remote character snapshots feed a bounded CPU-only appearance scheduler. Duplicate
appearance demand is merged using its best region/distance. Visible demand always
precedes the 1.5-view prefetch band; within a region, requests waiting at least
250 ms precede newcomers, oldest first, then distance and appearance ID. Time is
monotonic; this is an ordering policy, not a completion-latency guarantee. Demand
age survives position/region changes but is removed when demand disappears or
becomes ready. Prefetch remains best effort while visible demand exists.

Same-region active CPU work is stable even if a nearer actor appears. CPU work
is superseded only when it loses all current interest or visible demand displaces
prefetch. Budget waits use the same rule. Submitted GPU uploads are completed,
including when their actor disappears; this avoids upload-destructor waits during
snapshot refresh. Completed unused clips become normal eviction candidates.

AnimationDecodeWorker.requestCancel does not wait for running CPU access. The
single slot and its reservation remain occupied until collectCancelled observes
actual completion. Old output/errors are discarded and cannot start an upload or
be attributed to a new appearance. No second task is queued while draining.
AnimationLibrary maintenance collects cancelled work even when no candidate remains.
Blocking scene-exit/shutdown cancellation remains available and still protects
reader lifetime. This does not make an individual file read interruptible.

Telemetry adds animation_discarded_decodes, counting superseded CPU requests, not
budget waits or GPU cancellation. Ready + retired + pending accounting stays in
force during cancellation. Scheduler nodes/scratch capacity are reused between
stable snapshots, and retained demand is bounded by the existing 1024-actor limit.
There is no queue of obsolete snapshots. Metadata planning for tighter worker
reservations and per-request latency diagnostics remain follow-up work.

Headless tests verify visible/prefetch ordering, duplicate demand, same-region
stability, aging, bounded replacement, and cancellation with a deliberately held
CPU task: requestCancel must return before the test releases that task, while its
reservation and captured references remain live. Vulkan tests displace prefetch
with a visible character, cycle repeated complete replacements without stale
uploads, and verify submitted GPU uploads cannot be cancelled through this path.

## Exact background decode admission and load timing

Background progressive loads first plan canvas metadata on the CPU worker; no
RGBA payload is allocated or reserved during that phase. Once the exact byte
count is known, the worker checks its 32 MiB clip limit and the owner-provided
available-budget snapshot, then reserves that exact payload before decoding.
The builder validates metadata again with that exact limit before allocating
pixels. No new GPU work or reader queries run on the owner thread for this plan.
Metadata/descriptions themselves still consume bounded CPU memory; zero RGBA
reservation does not mean zero CPU memory usage.

An occupied slot is independent of reservedBytes. Queued/running metadata and a
ready error can occupy it while bytes are zero. Use AnimationLibrary.cpuPending
or streamingPending for lifetime/cleanup decisions, not pendingBytes > 0.
Nonblocking cancellation retains slot ownership until CPU access ends, including
zero-byte metadata. A second job cannot enter while draining. Existing immediate
submit with an explicit reservation remains available to headless worker users.

Only one owner-thread admission can allocate animation payload at a time. Ready/
retired restoration does not grow the accounted sum. Shrinking the hard budget
while a metadata/decode request exists is rejected even at zero reserved bytes;
collect/cancel that CPU request first. Increasing budget is safe, but an existing
job uses its original snapshot and may defer once before retrying. Ready + retired
+ pending RGBA remains within the hard budget; accounting excludes driver overhead,
staging and other resource classes as before. This refines reservation accounting;
it does not imply the old 32 MiB reservation was an actual 32 MiB allocation.

Runtime JSON adds animation_cpu_pending and background-load timing fields:
animation_load_samples/completed/mean_ms/p95_ms/p99_ms/max_ms,
animation_cpu_service_mean_ms, animation_upload_wait_mean_ms,
animation_load_cancelled and animation_load_failed. The window holds the latest
256 successful requests, with a separate lifetime completion count; recording and
summary use fixed storage. Cache hits and synchronous scene/progressive loads do
not start timing samples. Cancelled/failed requests increment separate counters,
not successful latency percentiles. clear resets all counters/window samples.

Total latency starts at first background submission and ends at ready-cache
publication. It includes queue scheduling, metadata/pixel CPU work, temporary
budget waits/retries and owner polling. It excludes demand waiting before first
submission. CPU service sums actual worker task wall time, including failed
metadata admission attempts for that same request. Upload wait starts after the
initial upload submission and includes chunk/fence/owner-poll delays; it is not a
GPU timestamp. These metrics therefore cannot alone establish server-demand
latency or pure GPU upload cost. Cancel/scene exit discards unfinished timings.

Headless gated tests exercise zero-byte occupied metadata, exact reservation
before pixel decoding, errors/oversized plans without decoder calls, cancellation
while metadata still owns reader access, oversized decoded capacity, and bounded
latency-window arithmetic. Real Vulkan tests hold the reader mutex on the owner
while submitting/cancelling background metadata, compare exact reservation with
actual RGBA usage, verify success-only timing, and reject a total budget of one
byte before any graphics pixel-file reads. The existing sixteen low-budget
appearance batches still verify eventual frame-fence recovery and teardown.

## Repeatable movement and snapshot churn

See [StreamingStress](../tools/StreamingStress/README.md) for the native CLI runner,
INI fields, reports and limits. ServerDemo.AnimationBudgetMiB is now configurable
(16..1024 MiB, default 512); visible/prefetch counts, catalog limit and random seed
are also explicit. StressFrames defaults to zero. An enabled script uses fixed
movement/snapshot simulation time and real CPU/GPU/frame timing, then closes after
the configured number of world updates. It requires a telemetry report and does
not coexist with the crowd benchmark. Manual WASD/N remain the default.

Lifetime frame FPS/max/over-33ms counters supplement the existing rolling window,
so early spikes cannot disappear when a long run overwrites the last 512 samples.
Scene-owned streaming diagnostics use scalar storage and are removed on exit.
The Python runner retains a bounded process-memory tail when psutil is present;
it does not measure driver VRAM. Low-budget cases report unresolved actors and
budget waits; clean process/script completion is not full-quality readiness.


## Same-process lifecycle soak

The full suite includes four native reload/retirement/cancellation cycles and
headless Python runner tests. For 100 cycles in a single process/device:

```powershell
ctest --preset dev-lifecycle-soak -V
ctest --preset asan-lifecycle-soak -V
```

These are lifetime checks, not FPS benchmarks. Both need installed assets and a
Vulkan desktop; use the developer environment for ASan. Optional quiescent RSS
sampling, growth gates, outputs and limitations are documented in
[LifecycleSoak](../tools/LifecycleSoak/README.md). This differs from repeating a
CTest executable in fresh processes, which cannot expose same-process buildup.


## SDK-free core CI

The independent project below builds nine native test suites plus two
Python protocol runners without the desktop project, Vulkan SDK/glslc, GLFW,
installed game files, Python development headers or NumPy. It is a selected core
subset, not the entire engine or all `unit` tests. It reuses the same sources and
CMake test definitions as the desktop build.

The map preparation suite exercises production CPU planning/pixel assembly using
synthetic reader implementations, including page admission, palette conversion,
ownership transfer and failure recovery. It links no asset-reader implementation
or graphics backend and needs no installed game files.
The sprite-memory suite checks fixed allocation accounting, simultaneous peaks,
invalid transitions, overflow rejection and unsupported diagnostics without Vulkan.
It also verifies live image-class footprints, class/global sum consistency and
atomic rejection of invalid metadata; see
[allocation breakdown validation](sprite-allocation-breakdown-validation.md).
The catalog suite checks bounded candidate scanning, deterministic version/serial
ordering, metadata filters, busy-reader retry and cancellation by destruction.
The map-worker suite checks its single slot, reservation retention, cancellation,
error recovery and captured-owner lifetime without starting a device/window.

```powershell
git submodule update --init third_party/googletest
cmake -S engines/tests/headless -B build/headless -G Ninja -DCMAKE_BUILD_TYPE=RelWithDebInfo
cmake --build build/headless --parallel 2
ctest --test-dir build/headless -V --no-tests=error --output-junit results.xml
```

Use an x64 developer environment for MSVC. A separate `build/headless-asan`
configuration with `-DCGL_ENABLE_ASAN=ON` enables the shared sanitizer flags.
No `setup_requirements.py` run or full dependency installation is needed here;
only the pinned googletest submodule and a Python 3 interpreter are required.
Python/psutil memory sampling remains optional; runner protocol tests handle its
absence explicitly.

`.github/workflows/headless-core.yml` runs this project on pull requests into
`develop`, pushes to `develop`, and manual dispatch. Windows 2022 and Ubuntu 24.04
each run ordinary and ASan configurations. Logs and CTest JUnit/diagnostics are
retained for seven days even on failure. No proprietary assets or self-hosted
GPU runner are used. Linux ASan requests leak detection; Windows MSVC ASan does
not provide equivalent LeakSanitizer coverage. This lane does not replace local
Vulkan, real-corpus, Python binding or long-session validation, and does not claim
a working Linux game client.


The initial four-job hosted matrix and local regression results are recorded in
[headless CI validation](headless-ci-validation.md).
