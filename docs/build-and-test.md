# Build and test

Use these commands from the repository root. On Windows use an x64 Visual Studio
Developer Command Prompt with MSVC AddressSanitizer installed. Install Ninja,
CMake 3.21+ (for presets), the Vulkan SDK including glslc, and Python with development
headers. Install the project's dependencies first:

```powershell
python setup_requirements.py --build_type RelWithDebInfo
cmake --preset dev
cmake --build --preset dev
ctest --preset dev-unit
```

Activate the intended Python environment before configuring; alternatively pass
`-DPython3_EXECUTABLE=...`. A worktree can reuse an existing dependency installation
by passing `-DCMAKE_PREFIX_PATH=.../third_party/build/RelWithDebInfo` to configure.
Put personal overrides in ignored `CMakeUserPresets.json`. Build directories are
`build/dev` and `build/asan`; older build directories are not updated by these presets.
The ordinary `cmake -S . -B ...` interface still works with CMake 3.16+.

## Test groups

| Label / dev preset | Runtime requirements |
| --- | --- |
| `unit` / `dev-unit` | No window, GPU initialization or installed game assets; synthetic files are generated by tests. Includes the Python/NumPy binding test when tools are enabled. Building currently still requires the desktop SDK dependencies. |
| `desktop` / `dev-desktop` | Vulkan device and desktop/window support. Includes rendering and client integration tests. |
| `assets` / `dev-assets` | Installed game corpus; some tests also need a desktop. |
| `memory` / `dev-memory` | Reader ownership, bounded scratch/cache, cancellation and scene teardown tests. Includes desktop/corpus tests. |

Labels overlap. The mixed `test_scene_lifecycle` executable is conservatively
marked desktop/assets/memory, including its CPU-only cases. These labels describe
runtime requirements, not independently buildable core modules. Future scene
refactoring can separate the mixed executable.

Presets run one test at a time because existing cases share generated settings and
working directories. Desktop tests also use a CTest resource lock to avoid
concurrent GPU/window tests. Every discovered case has a timeout; presets fail if
no test matches. Inspect the selected cases before running on another machine:

```powershell
ctest --preset dev-unit -N
ctest --test-dir build/dev --show-only=json-v1
ctest --test-dir build/dev --output-on-failure --no-tests=error
```

The last command runs **all** tests, without exclusions. Corpus tests read
`build/dev/bin/settings.ini`; set `General.EngineRootPath` to the directory containing
`bin/` and `map/`. Desktop map tests need `map/0/2100.dat` and `map/0/100.dat`.
Do not replace this shared test INI with a benchmark/server-demo configuration.
Settings generation can recreate this INI after changes to the settings schema.
Missing assets or GPU support are failures, not silently skipped tests.

## AddressSanitizer and resource lifetime

```powershell
cmake --preset asan
cmake --build --preset asan
ctest --preset asan-unit
ctest --preset asan-memory
```

Configure the ASan build's own `bin/settings.ini` before corpus tests. Tools are
disabled in this preset, so ASan does not need to load an instrumented Python module.
`CGL_ENABLE_ASAN=ON` also works with a custom build directory. MSVC uses
`/fsanitize=address`, debug information and non-incremental linking. STL container
annotations are disabled for compatibility with existing unsanitized dependencies;
this reduces container-boundary coverage. GCC/Clang use `-fsanitize=address` and
frame pointers. These compiler branches are not a claim of completed platform ports.

ASan catches memory access errors; a passing run alone does not prove absence of
leaks, especially on Windows where this configuration does not provide LeakSanitizer.
Ownership tests additionally check released references, pending-work cleanup and
bounded retained buffers. GPU tests check validation diagnostics and teardown.
Repeated scene/reload tests and process/GPU memory measurements remain necessary
for resource-cache changes. Driver allocations and cache residency must be tracked
separately from leaked objects. Do not compare ASan FPS against release performance.

For repeatable teardown/cancellation checks:

```powershell
ctest --test-dir build/asan -L memory --repeat until-fail:5 --output-on-failure --no-tests=error
```

## Interactive map demo and Python smoke check

```powershell
.\build\dev\bin\cgl-client.exe --settings .\build\dev\bin\server-demo100.ini
python -c "import sys; sys.path.insert(0, 'build/dev/bin'); import cgl; print('cgl import OK')"
```

Set the demo INI's asset root separately. WASD moves, N randomizes remote actors,
and R restarts. VSync is off in the demo configuration. This is an interactive
simulation, not an automated FPS regression gate. Python tools are built by the
`dev` preset; install tool requirements in the chosen Python environment as needed.

## Bounded runtime telemetry

General gameplay can use the same CPU frame-time mean/nearest-rank percentile
calculation as the crowd benchmark. In a custom INI:

```ini
[Telemetry]
Enabled=true
ReportPath=runtime-summary.json
```

Telemetry is off by default; the supplied server-demo100.ini enables it. Empty
ReportPath keeps the periodic console/title diagnostics without writing a file.
Report paths are relative to the process working directory; the parent must exist.
Use a different path from Benchmark.ReportPath. A failed report write is reported
as a client error and still goes through normal engine cleanup.

The runtime collector keeps exactly 512 sample slots. Its summary describes the
last up to 512 completed gameplay frames, not a fixed number of seconds or the
whole session; total_samples is a separate lifetime count. Initial loading is
excluded. Restart/transition stalls after gameplay starts remain observable.
Zero drawn actors can be correct for non-map scenes. Drawing only updates render
counters; sampling happens after the frame has been recorded/presented. Console
summary output is limited to every two seconds and its cost is included in that
frame's duration. Sample insertion and rolling summaries do not allocate heap
storage. World rendering still has its existing allocations; telemetry does not
claim to remove those.

FPS is 1000 divided by mean CPU frame duration. Update, render-loop and map-sort
CPU times are separate; render-loop time includes presentation/fence waits, not
GPU timestamp-query execution time. The title shows the previous completed frame
window when the local snapshot refreshes. When telemetry is disabled it says so.

Report status describes clean/error exit, not appearance-loading completion. A
frame-limited run can exit during initial loading with zero gameplay samples;
check total_samples before interpreting a report.

JSON reports include frame p50/p95/p99/max, counts above 1000/30 ms, draw counts and
resource snapshots taken before teardown. Animation and map RGBA fields count
cache-owned texture payload, with hover-outline bytes separate. Animation pending
bytes are the current CPU/decode or upload reservation, not an exact GPU resident
allocation; do not add them to other fields as a process/VRAM total. Driver,
pipeline, descriptor, staging, allocator overhead and reader scratch/cache bytes
are not covered. Usage snapshots borrow no resource ownership and clear to zero
when their caches are cleared.

The benchmark retains its existing bounded-by-config whole-run vectors, cold-load
latency reports and warmup behavior. Its full-run FPS/percentiles can differ from
the runtime collector's last-512-frame values. Basic runtime telemetry does not
yet provide per-request latency, hit/miss counts, GPU timers or eviction metrics;
those can be added at the responsible resource layers with later cache work.
