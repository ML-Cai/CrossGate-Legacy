# Build and test

Use these commands from the repository root. On Windows use an x64 Visual Studio
Developer Command Prompt with MSVC AddressSanitizer installed. Install Ninja,
CMake 3.21+ (for presets), the Vulkan SDK including glslc, and Python with development
headers. Install the project's dependencies first:

```powershell
python setup_requirements.py --build_type RelWithDebInfo
cmake --preset dev
cmake --build --preset dev
ctest --preset dev-unit
```

Activate the intended Python environment before configuring; alternatively pass
`-DPython3_EXECUTABLE=...`. A worktree can reuse an existing dependency installation
by passing `-DCMAKE_PREFIX_PATH=.../third_party/build/RelWithDebInfo` to configure.
Put personal overrides in ignored `CMakeUserPresets.json`. Build directories are
`build/dev` and `build/asan`; older build directories are not updated by these presets.
The ordinary `cmake -S . -B ...` interface still works with CMake 3.16+.

## Test groups

| Label / dev preset | Runtime requirements |
| --- | --- |
| `unit` / `dev-unit` | No window, GPU initialization or installed game assets; synthetic files are generated by tests. Includes the Python/NumPy binding test when tools are enabled. Building currently still requires the desktop SDK dependencies. |
| `desktop` / `dev-desktop` | Vulkan device and desktop/window support. Includes rendering and client integration tests. |
| `assets` / `dev-assets` | Installed game corpus; some tests also need a desktop. |
| `memory` / `dev-memory` | Reader ownership, bounded scratch/cache, cancellation and scene teardown tests. Includes desktop/corpus tests. |

Labels overlap. The mixed `test_scene_lifecycle` executable is conservatively
marked desktop/assets/memory, including its CPU-only cases. These labels describe
runtime requirements, not independently buildable core modules. Future scene
refactoring can separate the mixed executable.

Presets run one test at a time because existing cases share generated settings and
working directories. Desktop tests also use a CTest resource lock to avoid
concurrent GPU/window tests. Every discovered case has a timeout; presets fail if
no test matches. Inspect the selected cases before running on another machine:

```powershell
ctest --preset dev-unit -N
ctest --test-dir build/dev --show-only=json-v1
ctest --test-dir build/dev --output-on-failure --no-tests=error
```

The last command runs **all** tests, without exclusions. Corpus tests read
`build/dev/bin/settings.ini`; set `General.EngineRootPath` to the directory containing
`bin/` and `map/`. Desktop map tests need `map/0/2100.dat` and `map/0/100.dat`.
Do not replace this shared test INI with a benchmark/server-demo configuration.
Settings generation can recreate this INI after changes to the settings schema.
Missing assets or GPU support are failures, not silently skipped tests.

## AddressSanitizer and resource lifetime

```powershell
cmake --preset asan
cmake --build --preset asan
ctest --preset asan-unit
ctest --preset asan-memory
```

Client startup integration tests allow 1200 frames / 100 seconds under ASan,
compared with 240 frames / 50 seconds normally. Instrumented asynchronous asset
initialization can outlast the ordinary frame limit; scene readiness, expected
errors, clean shutdown and Vulkan validation checks remain required.

Configure the ASan build's own `bin/settings.ini` before corpus tests. Tools are
disabled in this preset, so ASan does not need to load an instrumented Python module.
`CGL_ENABLE_ASAN=ON` also works with a custom build directory. MSVC uses
`/fsanitize=address`, debug information and non-incremental linking. STL container
annotations are disabled for compatibility with existing unsanitized dependencies;
this reduces container-boundary coverage. GCC/Clang use `-fsanitize=address` and
frame pointers. These compiler branches are not a claim of completed platform ports.

ASan catches memory access errors; a passing run alone does not prove absence of
leaks, especially on Windows where this configuration does not provide LeakSanitizer.
Ownership tests additionally check released references, pending-work cleanup and
bounded retained buffers. GPU tests check validation diagnostics and teardown.
Repeated scene/reload tests and process/GPU memory measurements remain necessary
for resource-cache changes. Driver allocations and cache residency must be tracked
separately from leaked objects. Do not compare ASan FPS against release performance.

For repeatable teardown/cancellation checks:

```powershell
ctest --test-dir build/asan -L memory --repeat until-fail:5 --output-on-failure --no-tests=error
```

## Bounded runtime telemetry

General gameplay can use the same CPU frame-time mean/nearest-rank percentile
calculation as the crowd benchmark. In a custom INI:

```ini
[Telemetry]
Enabled=true
ReportPath=runtime-summary.json
```

Telemetry is off by default; the supplied server-demo100.ini enables it. Empty
ReportPath keeps the periodic console/title diagnostics without writing a file.
Report paths are relative to the process working directory; the parent must exist.
Use a different path from Benchmark.ReportPath. A failed report write is reported
as a client error and still goes through normal engine cleanup.

The runtime collector keeps exactly 512 sample slots. Its summary describes the
last up to 512 completed gameplay frames, not a fixed number of seconds or the
whole session; total_samples is a separate lifetime count. Initial loading is
excluded. Restart/transition stalls after gameplay starts remain observable.
Zero drawn actors can be correct for non-map scenes. Drawing only updates render
counters; sampling happens after the frame has been recorded/presented. Console
summary output is limited to every two seconds and its cost is included in that
frame's duration. Sample insertion and rolling summaries do not allocate heap
storage. World rendering still has its existing allocations; telemetry does not
claim to remove those.

FPS is 1000 divided by mean CPU frame duration. Update, render-loop and map-sort
CPU times are separate; render-loop time includes presentation/fence waits, not
GPU timestamp-query execution time. The title shows the previous completed frame
window when the local snapshot refreshes. When telemetry is disabled it says so.

Report status describes clean/error exit, not appearance-loading completion. A
frame-limited run can exit during initial loading with zero gameplay samples;
check total_samples before interpreting a report.

JSON reports include frame p50/p95/p99/max, counts above 1000/30 ms, draw counts and
resource snapshots taken before teardown. Animation and map RGBA fields count
cache-owned texture payload, with hover-outline bytes separate. Animation pending
bytes are the current CPU/decode or upload reservation, not an exact GPU resident
allocation; do not add them to other fields as a process/VRAM total. Driver,
pipeline, descriptor, staging, allocator overhead and reader scratch/cache bytes
are not covered. Usage snapshots borrow no resource ownership and clear to zero
when their caches are cleared.

The benchmark retains its existing bounded-by-config whole-run vectors, cold-load
latency reports and warmup behavior. Its full-run FPS/percentiles can differ from
the runtime collector's last-512-frame values. Basic runtime telemetry does not
yet provide per-request latency, hit/miss counts or GPU timers;
those can be added at the responsible resource layers with later cache work.

## Idle cache maintenance at scene transitions

```ini
[CacheMaintenance]
Enabled=true
AnimationTargetMiB=64
MapTargetMiB=64
```

These are the defaults, in the range 0..1024 MiB. They are soft **total cached
payload** targets, not replacements for the animation hard loading budget or a
physical VRAM limit. A zero target drops every eligible ready entry at a transition.
An additional fixed 1 MiB warm budget applies to hover outlines. Soft count limits
of two maps and sixteen outlines also bound CPU-only/zero-texture cache entries.
A zero byte target also sets that cache count target to zero. Live references
can keep usage above any target; they are never forcibly invalidated.

Ready animation, map and outline caches track successful acquisition/readiness
lookups and publication in least-recently-used order. After the old scene has
exited and been destroyed, before the next scene loads, the engine trims entries
that have no shared owners outside the cache until the target is met or no more
eligible entries remain. Recency metadata is stored with the cache entry and is
removed with it. There is no age-in-seconds/TTL policy in this step.

Reference count alone is **not** evidence of GPU completion: recorded draws borrow
raw renderer pointers. ClientEngine now moves cache-only victims to a deferred
ownership queue, tagged with the last successful graphics submission serial.
Frame slots record their serial only after successful queue submission. A
successful wait on a reused slot's fence advances completion; failed waits or
submissions do not. This proof applies to the single graphics queue used by this
renderer, not presentation or arbitrary future transfer/compute queues.

Each update collects entries whose serial has completed. Collection can lag GPU
completion by a frame/slot reuse; it never adds a fence poll, device waitIdle or
queue wait to maintenance. Allocation failure preserves the current cache entry;
earlier transfers stay queued. There are no raw owning callbacks or detached
resources. Pending decode/upload slots are not retirement candidates. Scene exit
still cancels/drains pending uploads, and shutdown still waits before clearing
both ready and retired ownership, before render-pass/device destruction.

The explicit library trimUnused API remains blocking for offline maintenance and
existing callers/tests. Do not use it for in-frame pressure eviction. retireUnused
and collectRetired are internal owner-thread APIs: callers must supply this
renderer/device lifetime's last submitted and acknowledged-complete serials.
Never substitute a CPU frame number or clear a live retired queue.

Telemetry keeps animation_rgba_bytes / map_rgba_bytes / outline_rgba_bytes as
ready-cache payload. Separate animation_retired_bytes, animation_retired_clips,
map_retired_bytes, outline_retired_bytes, retired_maps and retired_outlines show
queued ownership. animation_evictions, animation_evicted_bytes and
map_outline_evictions count cache removals, not completed GPU frees. Counters
reset on clear. Ready + retired + pending animation payload/reservation counts
against the hard animation budget; retiring an entry does not create free budget.
These are not physical VRAM or total process RAM measurements.

Warm resources below targets and externally held resources remain retained.
Progressive appearance loading now defers on temporary budget pressure and can
evict cache-only ready clips during gameplay. Synchronous scene/map loading still
fails if the new scene cannot fit alongside queued allocations. Reusing retired
assets and asynchronous scene-entry backpressure remain follow-up work. Re-entering
a just-retired asset can temporarily require two copies; do not interpret a soft
cache target as a strict peak-memory limit. This PR removes the retirement wait,
not synchronous map loading, upload cancellation waits or shutdown synchronization.

CPU tests cover LRU/pins, transfer allocation failure, zero-byte entries, ordering,
overflow, 1000 retirement/collection cycles and submission acknowledgement. Real
Vulkan tests submit map100 draws, drop scene owners, retire/reload three times,
verify weak references survive before fence acknowledgement and expire after it,
keep a pinned clip alive, and ensure retired bytes remain charged to the budget.
The existing blocking-maintenance tests remain. ASan, weak-reference expiry and
validation checks supplement each other; none alone proves absence of all leaks.

## Progressive animation budget pressure

AnimationBuilder distinguishes metadata admission failure from corrupt/missing
assets. AnimationBudgetExceeded includes required RGBA bytes and is raised before
palette/pixel reads. A progressive request that can fit the configured total and
32 MiB per-progressive-clip limits returns nullptr while free budget is too small,
retains one bounded request/required-byte record, and retries after collection.
It does not repeatedly decode pixels or permanently blacklist that appearance.
The background and owner-thread decode paths use the same admission behavior.
At zero free bytes, the background path initially records a one-byte admission
minimum; metadata planning determines the exact size once capacity becomes
available. This may require another pressure cycle before pixels can be decoded.
Missing/corrupt resources, invalid directions and clips exceeding a total/per-clip
limit remain real errors. Synchronous acquire keeps its existing throwing contract.

ClientEngine calls maintainStreaming once per update. It collects at most eight
completed clips, one map and two outlines; zero-byte entries count toward these
limits. When a progressive request is waiting, pressure retirement selects only
cache-only LRU clips, at most eight per scan, no more than once per sixteen update
calls. Cancelling/replacing a wait does not reset the scan cooldown.
Already-retired bytes are credited as future capacity before selecting
more victims, but cannot be used for an upload until acknowledged completion and
collection. No new waitIdle/fence wait is added. CacheMaintenance.Enabled=false
disables automatic pressure eviction as well as transition eviction; bounded
collection continues because pending GPU ownership must eventually be released.

These are work-count bounds, not hard CPU-millisecond bounds. Candidate LRU scans
still visit/sort the current cache. GPU object destruction and freeing a large map
can take driver/allocator time. If all clips remain pinned, the request keeps its
placeholder and waits without evicting live assets; it is not guaranteed to become
ready under an insufficient working-set budget. Increasing budget or releasing
owners can unblock it. Cancel/scene exit clears the wait record; shrinking budget
below an already-known waiting clip minimum is rejected until that wait is cancelled.

The server demo may switch a waiting (no upload submitted) request to the current
visible/prefetch candidate, or cancel it when no candidate remains. It still
finishes submitted uploads rather than cancelling GPU work on every snapshot.
Full scheduler preemption/fairness is not implemented here.

Telemetry adds animation_budget_deferrals (number of admission-deferral returns,
not elapsed frames) and animation_waiting_for_budget. Existing pending bytes stay
zero during a pure budget wait. Ready + retired + pending accounting remains in
force; these counters are not driver VRAM measurements.

Tests cover required-byte metadata errors without pixel reads, pinned pressure,
retired capacity remaining charged until frame-fence completion, eventual retry,
disabled eviction, candidate cancellation/reappearance, real errors remaining
errors, bounded destruction/retirement including zero-byte entries, and sixteen
small-budget snapshot batches cycling through eight distinct character appearances.

resource and rendering work and the estimated PR boundaries.
